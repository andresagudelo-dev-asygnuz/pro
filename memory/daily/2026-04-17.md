## G4 Sprint 1 PR D — Admin de cola (HU-002 §6)

- **Admin gating por whitelist de email.** Nueva env opcional `ADMIN_EMAILS` (coma-separada) en `lib/env.ts`; helper `lib/auth/admin.ts` exporta `isAdminEmail`, `getAdminUser` (cached) y `requireAdmin`. Comparación case-insensitive, tolera espacios; lista vacía ⇒ nadie es admin. Rationale documentado en el módulo: no hace falta tabla `admins` ni cambios de esquema para el MVP; el admin es un humano con email real. Post-MVP migraremos a tabla `admins` con auditoría.
- **Ruta `app/(app)/admin/verificaciones/page.tsx`** (server component, `dynamic = "force-dynamic"`). Layout `app/(app)/admin/layout.tsx` llama `requireAdmin()` ⇒ un no-admin cae a `/feed` sin 403/404 explícito (no revelamos la existencia de rutas admin).
- **Listado de pendientes vía service_role.** `lib/admin/age-verification-queue.ts::listPendingVerifications` hace select FIFO por `created_at` asc sobre `age_verifications` con status `pendiente`, join best-effort contra `profiles` para mostrar `full_name` / `username`, y genera signed URLs cortos (5 min TTL) para cada documento del bucket privado `age-verifications`.
- **Server Action `reviewVerification`** en `lib/admin/age-verification-actions.ts`: valida con `reviewVerificationSchema` (Zod), re-chequea admin vía `getAdminUser()` (defensa en profundidad frente a invocación directa), usa `service_role` para updatear la fila setando `status`, `reviewed_at`, `reviewed_by` y `rejection_reason` en un solo update. El filtro `.eq("status", "pendiente")` evita races entre admins — el segundo click pierde y recibe mensaje explícito. `revalidatePath("/admin/verificaciones")` + `revalidatePath("/", "layout")` para refrescar la cola y el banner del usuario.
- **Zod `reviewVerificationSchema`** con `superRefine`: aprobada sin motivo ok; rechazada exige `rejection_reason` 2–500 chars (trim + normaliza vacíos a null). `menor_edad` no se expone por UI (bloqueo permanente manual, ver ADR-003).
- **UI `components/admin/verification-review-form.tsx`** (client): botones Aprobar / Rechazar…, textarea inline condicional con validación nativa `minLength=2` / `maxLength=500`, cierre automático del panel tras success (patrón `reviewedAt` análogo a `uploadedAt` del form usuario).
- **Nav**: `app-nav.tsx` acepta `isAdmin?: boolean` y muestra link "Admin" condicional. `(app)/layout.tsx` resuelve admin con `getAdminUser()` en paralelo a `getProfile()`.
- **RLS intacta.** Mantenemos la policy `age_verifications_update_blocked` del PR A: el cliente autenticado no puede updatear nunca; sólo el service_role vía Server Action. PR D no agrega migración.
- **Tests vitest (+13, total 84)**: 7 casos de `reviewVerificationSchema` (aprobada/rechazada/motivo vacío/motivo>500/decision desconocida/UUID inválido/aprobada sin reason ⇒ null) + 6 casos de `isAdminEmail` (env no seteada/vacía/match/case-insensitive+espacios/no-match/null-undefined-vacío con `vi.resetModules`).
