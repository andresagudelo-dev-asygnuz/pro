## Lecciones aprendidas
- **Merges grandes de UI/landing pueden pisar dominio sin que CI lo detecte si las funcionalidades no tienen tests E2E.** Mitigación: revisar manualmente el `git diff --stat` de cualquier PR que toque > 30 archivos; opcionalmente añadir un workflow que flaggee PRs cuyo diff toca rutas de varios sprints distintos.
- **`db/migrations/` y `apps/web/supabase/migrations/` coexisten pero solo el segundo se aplica.** Toda migración nueva debe vivir bajo `apps/web/supabase/migrations/`. Cualquier archivo bajo `db/migrations/` es documental u obsoleto.
- **CI corre `pnpm lint` y falla con errores, no warnings.** El equipo acumuló 14 errores ESLint en `main` que CI debió haber bloqueado — investigar por qué pasó (posible push directo a `main` sin PR, o cache de CI).

## Reglas del proyecto
- **Toda migración SQL** vive en `apps/web/supabase/migrations/` con nombre `YYYYMMDDHHMMSS_descripcion.sql`. `db/migrations/` no se usa para producción.
- **PRs** siempre fetch del template antes de crear (`git_pr action=fetch_template`). Branches con prefijo `devin/<timestamp>-<descripcion>` o `feat/`, `fix/`, `chore/`.
- **CI debe pasar** (lint + typecheck + tests + build) antes de mergear. Nunca pushear directo a `main`.
- **Antes de cualquier merge** de PR que toque > 30 archivos, revisar el diff completo y confirmar que no se pisan rutas de dominio fuera del scope del PR.
