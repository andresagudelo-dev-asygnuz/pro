# Test plan · HU-002 Verificación de edad (RF-007)

Historia: `tasks/hu/HU-002.md`.
Migración canónica: `apps/web/supabase/migrations/20260417130000_g4_sprint1_auth_age.sql` (sección `age_verifications`).

## Scope

- Tabla `age_verifications (user_id, status, document_url, reviewed_by, reviewed_at, ...)`.
- RLS:
  - `age_verifications_read_self`: un usuario solo lee su propia fila.
  - `age_verifications_admin_all`: admins leen/escriben todas (identificado
    por `raw_app_meta_data->>'role' = 'admin'`).
- Flujo: `/verificacion` sube documento a bucket `age-verifications` (prefijo
  `user_id/`), crea fila en `age_verifications` con `status='pendiente'`.
- Admin (`/admin/verificaciones`) lista pendientes, aprueba/rechaza con
  motivo, actualiza status + `reviewed_by`/`reviewed_at`.
- Función SECURITY DEFINER `find_unverified_users(uuid[])` para bypasear RLS
  cuando un capitán valida a sus miembros (HU-005).

## UI smoke test

1. Signup como jugador (HU-001).
2. Login → `/verificacion`, subir PDF o imagen → "Estado: pendiente".
3. Logout + login como admin (poner `raw_app_meta_data='{"role":"admin"}'` en psql).
4. `/admin/verificaciones` → aprobar. Logout.
5. Login como el jugador → `/perfil` queda disponible (HU-003 gate).

## Deuda técnica

- Caso 6 (`find_unverified_users` RPC bypass) validado unit-level pero no
  verificado en Supabase real. Prioridad alta porque es el único mecanismo
  que permite a un capitán validar a sus miembros (HU-005).
- RLS admin distingue por `raw_app_meta_data.role='admin'`: considerar
  migrar a tabla `user_roles.is_admin` en G6+ para consistencia con los
  roles existentes.
