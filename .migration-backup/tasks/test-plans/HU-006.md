# Test plan · HU-006 Resultados + Standings (RF-005)

Historia: `tasks/hu/HU-006.md`.
Migración canónica: `apps/web/supabase/migrations/20260429140000_g4_sprint5_standings.sql`.

## Scope

- `tournament_matches(id, tournament_id, round, group_code, fixture_order,
  home_registration_id, away_registration_id, scheduled_at, venue,
  home_score, away_score, status, correction_window_ends_at, …)`.
- `match_events(id, match_id, event_type, minute, player_id, team_side, notes)`
  con enum de `event_type ∈ {gol, auto_gol, amarilla, roja, sustitucion}`.
- `status ∈ {programado, en_juego, finalizado, w_o, cancelado}`.
- Mat view `standings (tournament_id, registration_id, played, wins, draws,
  losses, goals_for, goals_against, goal_difference, points)` con índice
  único `(tournament_id, registration_id)` para `REFRESH MATERIALIZED VIEW
  CONCURRENTLY`.
- **Fix crítico Sprint 5 (PR #30):** `standings` se crea con `WITH NO DATA`
  y el único path de refresh usaba `CONCURRENTLY`. PostgreSQL prohíbe
  CONCURRENTLY sobre una mat view nunca populada → todos los refreshes
  posteriores fallaban silenciosamente. Fix: agregar `refresh materialized
  view public.standings;` (no-concurrent) al final de la migración para
  popularla una vez.
- Trigger `tm_after_finalize_refresh` (AFTER UPDATE ON tournament_matches):
  cuando `NEW.status='finalizado' AND OLD.status <> 'finalizado'`, refresca
  la mat view con `REFRESH MATERIALIZED VIEW CONCURRENTLY public.standings`.
- Regla trigger: solo se permite cargar resultados si el torneo está en
  `cerrado_inscripciones` o `finalizado` (raise `tournament_not_ready_for_results`).
- Algoritmo V=3, E=1, D=0. DG = GF − GC. Ordenamiento:
  points DESC → goal_difference DESC → goals_for DESC.

## UI smoke test

1. Como owner, abrir `/tournaments/[id]/matches/new` → crear match R1
   home=Team A vs away=Team B.
2. `/tournaments/[id]/matches` → ver fixture.
3. Entrar al match → cargar resultado 2-1 → finalizar.
4. `/tournaments/[id]/standings` → ver tabla ordenada con Team A arriba
   (3 pts, DG +1) y Team B abajo (0 pts, DG −1).

## Deuda técnica

- Proyección de `match_events.player_id` → stats agregadas por jugador
  (Bloque 4 del perfil) sigue fuera de scope desde HU-006.
- Correction window (`correction_window_ends_at`) modelado pero no enforced
  por trigger. En G6 agregar check de ventana antes de permitir updates
  post-`finalizado`.
- Caso 14/15 son los que cubren el 🔴 crítico de Sprint 5 — requieren
  validación SQL real (pendiente en sandbox por rate-limit ECR).
