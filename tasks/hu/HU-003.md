# HU-003 - Perfil tipo ficha (subconjunto MVP1 fútbol) con selector de visibilidad

## Historia
Como jugador verificado
Quiero cargar y editar mi perfil tipo ficha con el subconjunto MVP1 (fútbol) y elegir la visibilidad de cada campo
Para que promotores y otros usuarios vean sólo la información que yo decido compartir, manteniendo el resto privado.

## Criterios de aceptación (GIVEN/WHEN/THEN)
1. Llenado del núcleo obligatorio
- GIVEN un jugador verificado sin perfil completo
  WHEN guarda el perfil con los campos mínimos del núcleo MVP1 (nombre, edad, ubicación, disciplina fija `fútbol`, lateralidad, posición preferida, pie hábil)
  THEN el sistema persiste el perfil y lo marca como `completo para MVP1`.

2. Llenado de campos opcionales (Bloque 1 y 2 reducido MVP1)
- GIVEN un jugador con perfil completo
  WHEN agrega o edita campos opcionales (intereses, habilidades blandas — texto libre + tags, estatura, peso)
  THEN el sistema persiste los cambios; los campos no obligatorios pueden quedar vacíos sin bloquear el perfil.

3. Selector de visibilidad por campo
- GIVEN un jugador autenticado en la vista de edición del perfil
  WHEN cambia el nivel de visibilidad de un campo entre `público`, `promotores` y `privado`
  THEN el sistema persiste el nivel para ese campo del usuario y lo aplica en todas las audiencias inmediatamente.

4. Defaults sensibles al crear el perfil
- GIVEN un jugador que completa el perfil por primera vez
  WHEN el sistema aplica los defaults de visibilidad
  THEN los campos morfológicos (estatura, peso) quedan en `promotores` por defecto y el documento de identidad queda en `privado` sin opción de elevarse.

5. Consulta de ficha respetando visibilidad
- GIVEN un jugador A con campos configurados en distintos niveles de visibilidad
  WHEN un jugador B (`público`), un promotor (`promotores`) o el propio A (`privado`) consulta la ficha
  THEN el sistema muestra únicamente los campos cuyo nivel de visibilidad coincide con la audiencia, ocultando el resto.

6. Sección social (habilidades blandas) compuesta
- GIVEN un jugador editando su perfil
  WHEN llena la descripción libre de habilidades blandas y selecciona tags curados del catálogo
  THEN el sistema valida que la descripción no exceda el límite (500–1000 chars) y que los tags pertenezcan al catálogo cerrado, y persiste ambos subcampos.

## Dependencias
- RF-002 (`docs/01-requisitos-funcionales.md`) + modelo detallado en `docs/intake/04-requisitos-funcionales-borrador.md`.
- HU-001 + HU-002 (cuenta + verificación de edad aprobada).
- G3 ADR-002 (modelo de `visibility_level` por campo).

## Tareas técnicas
- [ ] Backend: endpoints `GET /api/profiles/:id`, `PUT /api/profiles/me`, `PUT /api/profiles/me/visibility` (por campo).
- [ ] Backend: aplicación de la visibilidad por campo al serializar el perfil según el rol/relación del solicitante.
- [ ] Backend: validación de catálogo cerrado de tags de habilidades blandas y del límite de caracteres de la descripción libre.
- [ ] Frontend: página `/profile/edit` con formulario por bloques, selector de visibilidad por campo y preview de "cómo me ven los demás" (tabs `público` / `promotores`).
- [ ] Frontend: página pública `/u/:slug` que respeta la visibilidad.
- [ ] DB: tabla `profiles` con los campos MVP1; tabla `profile_field_visibility(user_id, field_key, level)` (decisión final en ADR-002).
- [ ] QA: tests unit de serialización por visibilidad, integration del flujo completo, e2e de la matriz (campo × nivel × audiencia) para al menos 2 campos sensibles (peso, documento).
